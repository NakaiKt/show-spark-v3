# アニメシーズン視聴管理ツール（新規構築）

## 背景
アニメリアクション配信者が、新クール開始前のYouTube配信でリスナーと一緒に視聴アニメを選定している。現在Miroで運用しているが、動作が重い、自由度が高すぎて操作が難しい、出力がそのまま共有画像として使えない、という問題がある。これを専用ツールで置き換えたい。

## 実装したいこと

### 認証・全体
- Googleアカウントでログインできる
- ホーム画面はダッシュボード。シーズン一覧を更新日の降順で表示し、通算の確定本数やシーズン数を表示する
- シーズン（年 + クール）を作成でき、その配下にアニメが属する

### ボード画面（メイン）
- YouTube配信曜日を列にしたかんばん。左端が「未定」列、その右に月〜日の7列で計8列
- 上部の入力欄にタイトルを打ってEnterすると「未定」列にカードが追加される
- カードをドラッグして曜日列に移動すると、その曜日が配信曜日として設定される
- カードのワンタップで「確定 / 候補」を切り替えられる（ドラッグではない）
- カードサイズを小・中・大の3段階で切り替えられる。小は一覧性重視、大は画像を大きく表示
- 列ヘッダにその曜日の確定本数と候補本数が表示される
- カードをクリックすると詳細がモーダルで開く。背景を暗くし、背景クリックとEscで閉じられる
- 詳細モーダルでは 画像URL / 放送曜日 / 放送時刻 / 視聴媒体 / タグ / メモ を編集できる。保存ボタンは置かず自動保存とする

### タグ
- タグはユーザー単位のマスタとして管理し、シーズンを跨いで再利用できる
- 1つのアニメに複数タグを付けられる
- タグは色を持ち、カード上で視覚的な手がかりになる
- 選択時に既存タグをサジェストし、新規作成もできる
- 初期タグは登録しない（空から始める）

### 出力
- 確定したアニメだけを1枚のPNG画像として出力・ダウンロードできる
- 画像に載せるのは「配信曜日」と「タイトル」のみ。放送曜日・放送時刻・作品画像は載せない
- 曜日ごとに1行、その行にその曜日の確定作品が並ぶ構成

### 同時編集
- 同一シーズンを複数人が同時に編集でき、相手の変更が数秒以内に自分の画面へ反映される
- 編集権限はシーズンのオーナーが他ユーザーに付与できる

## 確定している制約・前提

### 技術構成
- フロント：Next.js + TypeScript + Tailwind CSS + shadcn/ui
- API：Python（FastAPI想定）を AWS Lambda + API Gateway HTTP API で提供。フロントとAPIは分離する
- 認証：Auth0。API Gateway HTTP API の JWT Authorizer で検証し、Python側に検証コードを持たせない
- DB：Supabase の Postgres（Supabaseは DB のみ利用し、Auth / Realtime / Storage は使わない）
  - Lambdaからの接続は Supavisor の Transaction mode（ポート6543）を使う。Session mode（5432）は接続枯渇を起こす。Transaction mode では prepared statement を無効化する必要がある
- 出力画像：フロント側でプレビューDOMをそのままPNG化する（html-to-image想定）。プレビューと出力が一致することを優先する。日本語Webフォントはセルフホストして同一オリジンから読む

### ドメインルール（重要）
- 「配信曜日」と「放送曜日」は別物。混同しないよう英語名で区別する
  - `stream_weekday`：配信者がYouTubeで配信する曜日。人が決める。出力画像に載る
  - `air_weekday` / `air_time_min`：アニメ自体の放送曜日・放送時刻。調べて入力する。編集画面のみ
- 深夜アニメは放送日基準で扱う。木曜25:30は「木曜25:30」であり金曜1:30とはしない
  - 時刻は 0〜1799 分で保持し、24:00〜29:59 を許容する
- 曜日は 1=月 … 7=日（ISO準拠）。表示順と保存値の順序を一致させるため
- 一覧のソート順は「配信曜日でグルーピング → 確定を上 → 放送が古い順 → 放送時刻の昇順」
  - 「放送が古い順」を絶対曜日で比較すると週跨ぎで逆転する（配信=日曜、放送=土曜25時のケース）。`((stream_weekday - air_weekday) % 7 + 7) % 7` の降順で比較する
- 曜日未指定のものは一覧・出力ともに最後に置く
- 「見送り」ステータスは作らない。見送る作品は候補のまま残す
- 削除は物理削除ではなくソフトデリート。誤操作の取り消しができること（見送り一覧としてUIに露出はさせない）
- 作品画像は自前で複製せず、外部サイトの画像URLを保持して参照する

### 規模・利用条件
- 1シーズンあたり候補30件前後、確定15件前後
- 同時編集者は2〜3人
- 配信中の操作画面は幅1920pxを前提とする
- 利用者の一人はPCに不慣れ。自由入力よりも選択・タップ操作を優先する。配信中に操作するため、機能の豊富さより壊れないことを優先する

### データモデル（議論で確定した内容）
```
season      id, owner_id, year, cour(1-4), title, created_at, updated_at
              unique(owner_id, year, cour)
season_member season_id, user_id, role(owner/editor/viewer)
anime       id, season_id, title, image_url, is_confirmed(default false),
            stream_weekday(1-7, null=未定), air_weekday(1-7),
            air_time_min(0-1799), medium_name, note,
            deleted_at, updated_at, updated_by
tag         id, owner_id, label, color, sort_order, unique(owner_id, label)
anime_tag   anime_id, tag_id
```
`user_id` / `owner_id` には認証プロバイダの sub クレームを入れる想定。

## 検討してほしいこと

- **リアルタイム同期の方式**。同時編集者2〜3人・30レコードという規模から3秒程度のポーリングで足りると見ているが、実装量と体験のバランスで判断してほしい。WebSocketを選ぶ場合は API Gateway WebSocket API + 接続管理が必要になる
- **同時編集時の競合解決**。レコード単位の Last-Write-Wins で十分と考えている。ただし詳細モーダルの自動保存とポーリングが競合するため、**フォーカス中のフィールドがポーリング結果で上書きされない仕組み**が必須。この設計を含めて検討してほしい
- **`season.updated_at` の更新契機**。シーズン作成・シーズン情報更新に加えて、配下のアニメやタグ紐付けの変更でも更新する必要がある。DBトリガーが書き忘れを構造的に防げると考えているが、他の手段も含めて判断してほしい
- **カードのドラッグ操作と他機能の干渉**。ドラッグ中のポーリング適用、ドラッグとクリック（モーダル起動）の判別、カードサイズ変更時のドロップ判定など
- **画像URLのリンク切れ時のフォールバック**表示
- **8列を1画面に収める際のレイアウト**。1920px前提だが、それ未満の幅で開いたときの折り返し方針

## 参考情報

- 現在の情報源はアニメイトタイムズのクール別ページ（例: https://www.animatetimes.com/tag/details.php?id=5806 ）。v1ではここを見ながらの手入力のみ
- 将来的に Annict GraphQL API（`https://api.annict.com/graphql`、`searchWorks(seasons: ["2026-autumn"])` で作品・放送情報を取得）による自動入力を検討している。ただしシーズン開始前は放送情報が未登録の作品が多いと想定されるため、手入力が常に成立する設計を崩さないこと
- シーズンのURLスラッグは Annict と同じ `2026-autumn` 形式に揃えておくと、後の連携が楽になる
